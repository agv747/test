## Три разных хранилища — главный источник путаницы

| Контур | Где | Чем менять |
|---|---|---|
| Browser demo | localStorage `rei.tw.demo.v2`, изображения в IndexedDB `rei-local-demo` | demo client + `applyCommand`; только этот браузер и origin |
| Private (shared) | `rei_records`, запись `(workspace,'TW')`; медиа в `rei_media` | `/api/execution/workspace`, `/commands`, спец-endpoints; нужен вход |
| Relational / legacy | таблицы из `shared/schema.js`, включая `skus` | legacy API |

**Обновление `skus` не обновляет `workspace.catalogue`.** Добавление relational `planograms`
не создаёт `workspace.plans`. Private-таблицы намеренно вне `TABLE_NAMES` и `/api/data`.
Без входа пользователь видит demo, даже когда серверная база заполнена — это штатное
поведение, а не признак пустой БД.

## Правила работы с данными

- `setup` — **add-only**: добавляет отсутствующие ID, существующие пропускает. Названия и
  artwork существующего SKU он не обновляет. `added: true` ничего не доказывает — сверять diff.
- Сохраняемые поля SKU: `id`, `code`, `name`, принудительный `market:'TW'`, `artworks`.
  `brand`, `gtin`, упаковка этим обработчиком **не сохраняются** — не обещать владельцу полей,
  которые handler отбрасывает.
- Команд `catalogue.patch` / `catalogue.delete` нет. Повторный setup это не заменяет.
- `revision` записи и ревизии планов/captures — **разные значения**. 409 `REVISION_CONFLICT`
  лечится перечитыванием и пересборкой команды, а не повтором старого payload с новым номером.
- `writeRecord` ограничивает payload 1 500 000 UTF-8 байт. `length(payload)` в SQLite считает
  **символы**, лимит — байты; это разные числа.
- Публикация делает план неизменяемым; следующая версия — через `plan.duplicate`.
  Не переписывать JSON опубликованного эталона, на который ссылаются исторические captures.
- Не использовать seed для обновления рабочего каталога. Не подменять серверные данные demo-JSON.
- Не создавать фиктивного admin actor ради недостающих прав.

## Известные границы реализации

- **Legacy API не защищён execution-авторизацией.** В `worker.js` ветки POST `/api/mutations`
  и `/api/migrate` не вызывают `getActor`/`authorize`; `/api/data` — не private endpoint.
  Не использовать это как обход входа; при работе с чувствительными данными сначала закрыть.
- **Мультирыночность не завершена.** `readWorkspace()` читает ровно `workspace/TW`;
  `blankWorkspace`, права и часть обработчиков привязаны к TW. Переименование модулей в UI
  этого не изменило. Глобальная замена строк `TW`/`SG` — не миграция.
- Аутентификации в legacy-контуре нет вообще: ключи провайдеров тратит любой, у кого есть URL.

## Среда этой сессии (проверено)

Egress наружу закрыт: `api.cloudflare.com` и `*.workers.dev` дают `000` / `403 CONNECT tunnel
failed`. Cloudflare-credentials в окружении нет, `~/.wrangler` отсутствует. **Единственный путь
к D1 — MCP-сервер Cloudflare**, и он часто отваливается после каждого вызова: инструмент
приходится перезагружать через ToolSearch. Следствие: любая выгрузка из D1 проходит через
контекст модели, то есть полученный файл — копия записи, а не её байты. Для строгой сверки
нужен полный SHA-256 точных байтов, а не длины разделов и не усечённый хеш.

## Демо-workspace переиспользуется, а не пересобирается

`loadDemo()` в `client.js` возвращает то, что лежит в localStorage, а `upgradeDemoCatalogue`
**только добавляет записи каталога** — слоты сохранённого плана он не трогает. Поэтому любое
изменение демо-данных не доходит до браузера, который уже открывал модуль: новые SKU приезжают
в справочник, а планограмма продолжает ссылаться на старые. Чтобы изменение дошло, надо
**поднять версию ключа** `DEMO_KEY` (сейчас `rei.tw.demo.v2`). Старый ключ не удаляется.

Вторая копия тех же данных — статика `public/demo/tw/` (`setup.json`, `planogram.json`,
`F1–F3.svg`). Она целиком выводится из `buildTaiwanDemo()`; после изменения демо-данных
запускать `npm run demo:tw`, иначе файлы останутся от прошлой версии.
